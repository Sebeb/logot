## System Design

Logot's detailed performance mode presents three widgets through the same widget registration, instantiation, refresh, labeling, and pinned-overlay framework: Performance Overview, CPU Allocation, and GPU Allocation. Performance Overview shows aggregate frame, CPU, GPU, and FPS history. Each allocation widget has the same width as Performance Overview, with its color-coded history and a narrow current-value bar above a top-ten legend. The allocation legend gives source names the row width, displays timing to two decimal places inside a compact color-matched pill, and omits percentages to keep the list readable at pinned-widget size. CPU Allocation can show render timing, whole-frame timing, or both.

The allocation legend uses ranking hysteresis to remain readable while neighboring sources fluctuate. A lower source must lead the source immediately above it by more than three percentage points continuously for one second before the two exchange positions. Falling back to a three-point-or-smaller lead resets that pending overtake. Sources that enter or leave the current top ten are still added or removed immediately.

Overview and allocation histories use the same persisted graph time-range setting, exposed at `/dev/performance/time_range`, and the same FPS-derived visible sample window. The setting lives under the shared performance namespace because it affects both the overview widget and allocation widgets. Allocation histories are also trimmed to that visible window, bounded by Logot's global performance-history cap, so CPU/GPU allocation widgets do not keep growing hidden history after the selected window has passed. Logot marks internally generated "not sampled this frame" placeholders separately from explicit unavailable samples; allocation widgets filter to available samples for rendering while snapshot export still keeps the frame-numbered history. The history renderer maps every integer x pixel in the graph to the nearest available sample and draws a one-pixel-wide stack for that column, which avoids fractional bar widths and skipped unavailable columns exposing dark seams between bars.

The stacked history and current-value bars follow the source-list order from top to bottom. The first source in the legend is the top band in the graph, and the gray `Other` band sits beneath listed sources when present. This makes color/order changes caused by ranking hysteresis visible in both the list and graph at the same time.

During a running project, F3 cycles four persisted performance-display states: hidden, FPS-only, Performance Overview, and Performance Overview plus CPU and GPU Allocation. Shift+F3 cycles the same four states in reverse, so a state can be reached in either direction. Each allocation widget joins the detailed state only when the profiler bridge (and, for GPU, the active renderer) can provide that source timing; unavailable timing is not pinned as an empty diagnostic panel. When neither CPU nor GPU allocation data is available the detailed state would be indistinguishable from Performance Overview, so it is skipped in both directions: F3 steps from Performance Overview straight back to hidden, and Shift+F3 steps from hidden straight to Performance Overview. The standalone FPS counter is unpinned whenever Performance Overview is pinned because the overview already carries FPS history. The selected state is saved in Logot's settings file, so the same pinned performance display is restored on the next project session; a saved detailed state falls back to Performance Overview when the session that restores it has no allocation data. Opening the command palette also allows CPU mode, allocation update speed, graph time range, and JSON performance snapshots to be controlled.

All three detailed widgets are pinned to the top-right corner. A corner is allowed to wrap into adjacent columns when its rows would exceed the usable viewport height. Display-variable columns use the viewport and edge insets as their available width; opposing corners reserve space for each other before text is wrapped. The earliest rows remain closest to their requested corner, so Performance Overview stays at the extreme right while CPU Allocation and GPU Allocation form a column immediately to its left on a short viewport. This preserves the existing pin model and avoids clipping at larger Logot UI scales.

The command palette keeps pinned items out of its root directory, where they would otherwise duplicate unrelated top-level commands. Instead, the `pins` directory contains a high-priority `pinned variables` group whose entries lead directly to each current pin and its actions. `/pins/view` remains the textual summary command, while `/pins/<encoded-address>` is the navigable palette route; reserving real `pins/*` commands takes precedence over a same-named pin.

Pinned display-variable rows normally keep the compact title-and-value presentation. If the title and value cannot fit together on one line within their allocated width, or the value contains explicit line breaks, Logot instead renders the title followed by the value in wrapping paragraphs beneath it. Paragraph layout avoids RichText table cells imposing an intrinsic width larger than the available lane. Authors can make that stacked layout authoritative by passing `{"wrap_value": true}` as the trailing options dictionary to `Console.add_display_variable()` or `Console.pin()`. Pinned values retain their complete text, including counts, BBCode formatting, and explicit newlines. Declared prose is allowed to wrap across every line it needs; undeclared values retain the compact presentation when they fit. Command-palette truncation rules are unchanged. No pin API, options dictionary, saved corner, saved order, visibility preference, or render-scale setting changes.

Shift+Return executes the selected command without closing or clearing the command palette, which is useful for repeated actions. Because a command can remove the item or dynamic route currently being viewed, Logot checks the retained path after execution. A path is kept exactly as typed whenever it still filters to at least one available option, even if the text is only a partial filter rather than a registered command. Only a filter with no results walks upward to the nearest registered ancestor; if no ancestor remains, it returns to `/`.

Logot test cases can also be supplied by a host whose test body is not GDScript. The host creates a `LogotExternalTestCase`, assigns its metadata and a callable body, and registers it with `LogotTestManager.register_test_case()`. The manager treats that case like a discovered test, including command registration, scene setup, result persistence, and reporting. Registration is explicit rather than based on scanning another language's source files, which keeps Logot independent of any one host language or reflection system. Registered cases survive `refresh()` until the host removes them with `unregister_test_case()`.

An external body receives the case and the normal `LogotTestContext`, then calls `complete()` when its work has finished. Completion can happen during the body call or later. The case records synchronous completion before deciding whether to await its signal, so an immediately completed body cannot leave the manager waiting for an event that already fired. A missing callable records the `external_body_missing` failure and returns without waiting.

Allocation collection depends on the debug-only engine singleton `LogotProfilerBridge`. Visible allocation widgets issue short renewable capture leases, meaning collection runs only while it has a foreground consumer. Render CPU requests the visual profiler, whole-frame CPU requests script profiling, and GPU adds an independent GPU-capture lease. The separate GPU lease matters on Metal: a CPU render allocation widget can keep Godot's marker stream active without permitting timestamp counter samples, while a visible GPU widget or pending snapshot enables both Metal sampling and viewport whole-frame measurement. Stock or release Godot builds expose a clear unavailable state instead of fabricated timing data.

Projects can register a Whole Frame CPU source group through `Console.register_performance_script_source_group(group_path, display_name, signature_prefixes)`. Matching per-function self-time and call counts are replaced by one aggregate row during ingestion, before percentages and history are calculated, so subsystem totals remain visible without double-counting the underlying functions. Groups affect presentation only: they do not enable profiling or add timing calls to project hot paths.

The allocation widgets are deliberately cheaper than the profiler data they display. By default they sample allocation collection at 4 Hz, using the same cadence for rebuilding their GDScript snapshot and redrawing the stacked graph instead of holding Godot's render visual profiler open continuously. The `/dev/performance/allocation/update_speed` setting persists an update rate from 1 to 60 Hz for users who want slower diagnostic overhead or faster updates. Test-mode widgets bypass the redraw throttle so deterministic Logot tests can inject histories and assert immediate state changes.

Render-source capture uses Godot's visual profiler, which consumes timestamp query slots even when Logot only needs CPU marker durations. Large projects can exceed Godot's default `debug/settings/profiler/max_timestamp_query_elements` value of 256 and spam `Tried capturing more timestamps than the configured maximum`, which itself can heavily reduce FPS. Projects that use Logot render-source profiling should raise that project setting before startup; the Adventure worktree currently uses 4096.

## System Implementation

`logot.gd` registers `dev/performance/overview`, `dev/performance/allocation/cpu`, `dev/performance/allocation/gpu`, the shared `dev/performance/time_range` setting, and the allocation refresh setting at `dev/performance/allocation/update_speed`. `_cycle_performance_pin_mode(reverse)` advances F3 through `_next_performance_pin_mode()` (`hidden`, `fps`, `overview`, `detailed`) or, when `reverse` is true for Shift+F3, steps backward through `_previous_performance_pin_mode()`; both skip `detailed` unless `has_performance_allocation_data()` is true, so the cycle lengths and skip points match in either direction. `_set_performance_pin_mode()` applies each state to the same pinned-display-variable framework used by other Logot rows. Hidden mode pins nothing, FPS mode pins only `dev/performance/fps`, overview mode pins only `dev/performance/overview`, and detailed mode pins Performance Overview plus CPU Allocation and GPU Allocation as `_should_pin_cpu_performance_sources()` and `_should_pin_gpu_performance_sources()` confirm useful data is available. `_save_performance_pin_mode()` and `_load_performance_pin_mode()` persist that state and allocation update rate under the shared performance settings section in `user://console_filters.cfg`. `widgets/performance_widget_base.gd` supplies the common Logot widget lifecycle used by the overview and allocation widget scripts.

`performance_source_monitor.gd` owns bridge discovery, frame-numbered history, source aggregation, whole-frame remainder calculation, time-window retention, compact widget snapshots, and snapshot serialization. The allocation widgets retain no more than the selected visible sample count, up to the global 500-sample performance cap, rank the current top ten, preserve stable palette colors for continuing sources, and render sampled histories through the widget's pixel-resampling pass rather than by drawing one variable-width rectangle per profiler sample. Snapshots are available through the GDScript API and `/dev/performance/allocation/snapshot`, and are saved beneath `user://artifacts/performance_snapshots/`.

The profiler-enabled Godot build applies the ordered patches documented in [`native/godot_patches`](../../native/godot_patches/README.md) to the pinned 4.7 source. The active macOS path is `MTL3::RenderingDeviceDriverMetal`. Its first timing layer records real `MTLCommandBuffer` start/end times and uses them as a whole-frame fallback without interpolating pass values. Its second layer uses the timestamp common counter set when stage-boundary sampling is supported: pending Godot markers are attached to the next render, compute, or blit pass boundary, with a trailing sampled blit encoder preserving a final marker that has no following pass. Counter ticks are calibrated against correlated CPU/GPU timestamp pairs and resolved into nanoseconds. Invalid or co-located samples inherit a neighboring value, and decreasing values clamp to the previous timestamp, so source deltas become zero instead of underflowing.

The bridge reports `gpu_timing_mode` as `unknown`, `none`, `total_only`, or `breakdown`. In `total_only` mode the GPU widget shows the real frame total with an explanatory note and deliberately suppresses the apparent final-source delta created by the fallback mapping. In `breakdown` mode it displays positive per-source intervals from Metal counters. `logot.gd` renews the bridge's independent GPU gate and `viewport_set_measure_render_time` only for a visible GPU consumer or snapshot. When that lease expires, the driver ignores timestamp writes, creates no pending samples, and attaches no sample buffers even if CPU visual profiling remains active.

`logot_display.gd` stores one horizontal corner container containing one or more vertical row columns. `_get_pinned_overlay_usable_rect` subtracts the four existing edge overrides and the eight-unit margins from the actual viewport canvas rectangle. Layout never treats CSS pixels as canvas units. `_layout_pinned_overlay_rows` measures each corner's natural demand, leaves compact geometry intact when opposing demand fits, and reserves horizontal space when it does not. Vertically opposing groups whose spans intersect reserve portions of the usable height. `_layout_pinned_overlay_corner_columns` greedily fills columns using measured wrapped heights, tries bounded column width allocations when height requires more columns, and reverses column order for right-hand corners. Native widget minima remain authoritative. Horizontal allocation reserves each corner's largest native widget minimum before assigning the remaining width to opposite wrappable text. If opposing native minima already exceed the usable width, both widgets retain their minima and may overflow; the allocator does not manufacture a finite-fit result. Rows and interactive descendants keep their identities while disposable column containers are rebuilt; the focused control is restored after reparenting. This behavior is generic to pinned Logot widgets and display variables rather than special-cased for performance widgets. Runtime polling uses a pinned-overlay layout signature covering visible addresses, effective corners, row sizes, viewport size, safe-area overrides, and corner redirects. When the signature is unchanged, Logot refreshes widget content without rebuilding the pinned row/column tree every frame; a slow fallback poll still lets mouse-corner redirects update.

For display-variable rows, `_should_stack_pinned_display_variable_value()` first honors the author declaration, then detects explicit value line breaks and measures the title and unformatted value text using the row’s active font. `_append_pinned_display_variable_row_text()` selects either the standard two-column table when its cells fit or a wrapping paragraph title/value layout. Width budget is part of the row render-cache signature, so viewport/inset changes and getter updates regenerate wrapping and its minimum height before packing. Command columns propagate the declaration through their render snapshots and cache signatures, measure prose into a width-dependent line array, and rebuild cumulative row geometry after width or scrollbar changes. Scrolling, scrollbar ranges, drawing, and hit-testing all consume those measured heights. The test `command_palette_pinned_variables_test.gd` covers the legacy triggers, declaration propagation, rendered N-line wrapping, and mixed-height hit-testing.

The command palette builds pin aliases dynamically from the active pinned-address set. `logot_display.gd` places those aliases below `pins/`, labels them with their decoded address, and assigns the dynamic pin entries the negative-priority `pinned variables` group while keeping the root `pins` tier with the other console commands. `logot.gd` resolves the same aliases for execution before forwarding their pin/unpin actions, but never replaces a registered `pins/*` command such as `pins/view` or `pins/clear`. `tests/logot_cases/command_palette_pinned_variables_test.gd` verifies that a pin is absent from root autocomplete, present directly under `pins`, and that the dynamic group sorts above normal entries.

Both the runtime submission path in `logot.gd` and the editor submission path in `editor/logot_editor_panel.gd` call `logot_display.gd`'s `reconcile_retained_command_path()` after a Shift+Return command. The display first rebuilds the retained input's tier matches and stops if any remain. Otherwise it resolves aliases, compares the retained path with the newly rebuilt registered-address hierarchy, and removes path segments until it finds a valid command or parent tier. Setting the fallback path is followed by the normal deferred text-change autocomplete flow, which rebuilds and shows the command palette just as editing the trailing `/` would. `tests/logot_cases/shift_submit_path_recovery_test.gd` covers filter preservation, nearest-ancestor recovery, root fallback, and palette visibility after both fallbacks.

`testing/logot_external_test_case.gd` implements the language-neutral adapter. Its `body` callable is invoked as `body.call(self, ctx)`, and `complete()` is idempotent so duplicate completion attempts do not emit duplicate signals. `testing/logot_test_manager.gd` stores explicitly registered cases separately from `_tests_by_id`; discovery rebuilds `_tests_by_id` and then validates and reapplies the registered set. Public registration and removal rebuild dynamic console commands and emit `tests_changed`, so the panel and command surface update immediately. The existing validator enforces the same identifier, scene, and duplicate rules for discovered and registered cases.

`tests/logot_external_test_case_adapter_test.gd` is the process-local headless regression test. It verifies refresh persistence, real manager execution and result reporting, unregister refusal, synchronous and deferred completion, and the missing-body failure. Run it with `godot --headless --path <logot-checkout> --script res://tests/logot_external_test_case_adapter_test.gd` after the project has completed its normal import scan.

The deterministic behavior suite is `/test/logot_performance_sources`; it verifies registration, shared widget lifecycle, top-ten calculations, graph behavior, snapshots, and top-right pins. `/test/logot_performance_sources_visual` captures the three-widget layout, while `/test/logot_performance_sources_native` validates live bridge collection and must run with a rendering-capable profiler-enabled Godot build.

### Host presentation theme

The runtime Logot node accepts a nullable exported `presentation_theme`. When supplied, the in-game UI instance receives it before entering the display tree and before display initialization captures base font sizes. Null preserves the existing vendor and editor presentation. This is a host configuration seam, with no project-specific default or branch. Input-method percentages, persisted settings, command palette, history and full log formatting retain their existing ownership.

### Responsive console footer

The scene-owned footer keeps the native input HBox and its existing action controls, with the collapsed-filter VBox as a separate sibling. Its generated filter row uses native HFlowContainer layout, preserving all seven original levels, order and handlers while wrapping at the available width. Input remains independently usable as filter counts grow. No polling, manual viewport geometry, hidden controls or font-size workaround is added. Both runtime and editor display composition retain the input-row API and palette/history ownership. The responsive_console_input test exercises 780/520 resizing, keyboard/touch modes, filter cycling, focus/caret, history and palette.


### Static widget sibling ordering

`add_widget(address, scene_or_path, description = "", group_name = "", group_priority = 0, default_minimum_size = Vector2.ZERO, display_label = "", display_order = 0)` accepts an optional ascending integer order. Existing callers retain alphabetical tier ordering because their orders are all zero. Group priority and name, then search score, still take precedence; equal orders fall back to the tier name. Orders apply to direct widget tiers, not their parent menus. Static ordering does not enable drag handles or register movement commands. If an orderable command shares a widget tier, its existing drag order takes precedence.

`set_widget_display_order(address, display_order) -> bool` changes typed or dictionary widget metadata in place and refreshes live displays through the existing catalog invalidation path. It returns false for missing widgets and true for existing widgets, including unchanged values; unchanged values skip invalidation. Address normalization matches registration and removal. The shared palette update retains columns and embedded controls for the same widget path, preserving their focus, caret and unsaved drafts. Removal erases the metadata with the widget; a new registration starts with its own order. Ordering is caller-owned metadata and is not persisted by Logot.

`tests/logot_cases/widget_display_order_test.gd` exercises the real sibling match builder and open multi-column palette, including legacy defaults, explicit orders, ties, group priority, live update, registry/column/widget identity, focused drafts, no-op updates, removal and re-registration. The existing `orderable_groups_shortcuts_and_highlights` suite remains the regression for mutable drag ordering.


## Responsive Pin Verification and Limits

The focused private regression lives in `tests/private_pinned_layout/pinned_display_responsive_layout_test.gd`. It needs a private context with a SceneTree and Theme, so it is deliberately outside the default `tests/logot_cases` discovery root. `prepare.py` copies its unchanged bytes to the original case path inside each isolated fixture, where `runner.gd` loads it directly. Preparation copies only the display script, log-level script, base test class, three SVG import dependencies, a supplied font, fixture theme, case, runner, and OS-userdata proof. Private project settings enable a unique relative custom userdata token and contain no autoloads or enabled editor plugins. The theme is loaded after import rather than during cold bootstrap. `run.py` requires a coordinator gate label, checks frozen hashes, verifies the exact Godot 4.7.2 banner and actual OS userdata directory before each nonproof engine process, and stops on engine errors, timeout, leaked resources, or incomplete collection.

The same frozen case collects 168 assertions against the base and candidate. Real version, FPS, and DEV-summary rows use the actual supplied rainyhearts font at size 40. CSS widths 360 and 390 are modeled as canvas widths 720 and 780 at canvas-to-CSS ratio 0.5, and 360 and 390 at ratio 1. The case checks containment, row collision, complete text, rendered width and wrapping height, width-only resizing, getter value changes, four corners, and interactive-control identity, draft, caret and focus. Unlimited content is checked only for retention. The accepted focused run collected 168 assertions before and after: baseline 154 passed and 14 failed, candidate 168 passed. All baseline failures and process outputs remain in the versioned evidence directory. This is package evidence, with no actual host scene, browser, screenshot, touch input, performance-widget sizing, or normal-suite acceptance implied.

Existing `command_palette_pinned_variables`, `render_scale_settings`, `command_palette_widget_placement`, `widget_display_order`, and `logot_performance_sources` cases remain callable through `tests/run_logot_test.gd`. They need their normal Console/Main and import dependencies, including their visual checkpoints; the minimal focused runner does not provide that environment. They were not run in this gate. A future bounded run must create and prove an isolated project first and enforce an external timeout; the existing normal runner has no wall-clock timeout itself.

There is no universal finite-fit guarantee. Text wider than its lane wraps completely; native widgets can still impose larger minimum sizes. Excess rows, a single paragraph taller than its usable lane, inset reservations consuming the viewport, or multiple irreducibly wide widgets can exhaust the available area. Existing layout behavior keeps those pins and content, with overflowing geometry possible. This change introduces no hidden truncation, forced unpinning, reduced font sizes, or new scrolling UI. A general overflow-navigation interface would require a separate design decision. The provided finite default cases have explicit containment and no-overlap assertions.


The normal-lifecycle compatibility gate for the original candidate is recorded separately in `tests/private_pinned_layout/compatibility_evidence_01`. It used the unchanged `tests/run_logot_test.gd`, which creates the actual Logot node and runs its normal initialization, manager, context, and Main scene. `command_palette_pinned_variables` passed all 24 code assertions, with its single visual checkpoint explicitly skipped because screenshots are unavailable headlessly. `render_scale_settings` passed all 20 code assertions. The registered pin case collected 73 assertions and passed 69 on the original candidate, compared with 60 on the base. The candidate as a whole therefore failed that gate. Two narrow mixed-widget collisions motivated the subsequent 16-line minimum-reservation addition, which was subsequently verified in its fresh gate described below; no host acceptance follows from these package results.

The other two registered-case failures were a fixture precondition: removing the last pin marks its row for deletion and returns from the empty-overlay refresh before reconstructing columns. The last empty column remains. The legacy append-only helper then added two columns to that existing column, so the old check counted three on both base and candidate. The corrected private normal-compatible case asserts the one-empty-column state after pending deletions settle, then gives the helper a newly created, asserted-empty fixture container and restores the original mapping afterward. It does not change production cleanup behavior. The corrected case adds explicit retention/minimum/corner checks for two native widgets whose opposing minima cannot fit, bringing its expected collection to 79 code assertions. The same case bytes are prepared for the base and new candidate.


The reviewed minimum-reservation candidate subsequently passed its fresh exclusive headless gate, preserved in `tests/private_pinned_layout/compatibility_evidence_02`: 24 pinned-variable code checks, 20 render-scale checks, 79 registered-pin checks, and the unchanged 168 focused checks, totaling 291 code assertions. The pinned-variable visual checkpoint was explicitly skipped by the real manager because screenshots are unavailable in headless mode; it provides no rendered visual acceptance. The registered case proved the one-empty-old-column precondition and the fresh-container legacy-helper premise, the finite two-column geometry, mixed native-widget/prose fit at 360/390, real registry/control/focus/draft/caret preservation, and retention of opposing minima that cannot fit. Bootstrap emitted font/SVG resource UID fallback warnings and loaded their imported dependencies by the exact text paths; those warnings are preserved rather than described as a warning-free run. No parser, import, engine runtime, leak, timeout, incomplete collection or teardown error occurred. All actual OS-userdata proofs and engine processes exited 0. Source hashes remained frozen, private userdata was cleaned, no fixture engine process remained, and canonical/cache/icon/normal-preference boundary manifests matched exactly. This closes the bounded package compatibility gate, with saturated-height, universal finite-fit and actual host/browser/visual acceptance still outside the claim.
